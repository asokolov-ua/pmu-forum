# Форум національної ідентичності · ПМУ

Окремий застосунок для форуму 27–28 листопада 2026 року в Києві. Участь безкоштовна, від 16 років; 100–120 учасників, конкурсний відбір. Чинний сайт ПМУ не змінюється.

## Локальний запуск

Потрібні Node.js 22.12+ та npm. У цьому каталозі:

```powershell
npm ci
npm run dev
```

Відкрити `http://127.0.0.1:4322`. Без налаштувань сервіси не викликаються, анкети доступні для перегляду, надсилання закрите. Дані анкети живуть лише у відкритій вкладці; localStorage не використовується.

```powershell
npm run check
npm test
npm run build
```

Стек: Astro 7, TypeScript, Tailwind CSS 4, Vercel, PostgreSQL у Supabase, Telegram Bot API. Astro 7 обраний після аудиту залежностей: гілка 6 мала відомі вразливості. `package-lock.json` фіксує перевірені версії.

## Структура

- `src/pages/index.astro` — лендинг.
- `src/data/forum.ts` — тексти, теми та схема обох анкет.
- `src/components/RegistrationForm.astro` та `src/scripts/registration.ts` — трикрокові анкети.
- `src/pages/api/applications.ts` — валідація, обмеження спроб, збереження.
- `src/pages/api/telegram/webhook.ts` — дії організаторів і експорт.
- `src/pages/api/telegram/retry.ts` — захищений повтор сповіщень.
- `supabase/migrations/001_forum.sql` — таблиці, закритий доступ, функції та черга.
- `tests/applications.test.ts` — серверна валідація, доступ, помилки сервісів та експорт.
- `tests/database.test.ts` — виконання SQL-міграції в локальному PostgreSQL, транзакції, права та історія.
- `QA.md` — результати перевірки та її межі.

## Підключення Supabase

1. Створити окремий Supabase-проєкт, обрати регіон та налаштувати доступ організаторів.
2. Виконати `supabase/migrations/001_forum.sql` у SQL Editor один раз. Він створює таблиці з RLS; публічний доступ заборонений, працює лише серверний `service_role`.
3. Скопіювати `.env.example` у `.env` та заповнити `SUPABASE_URL` і `SUPABASE_SECRET_KEY` (секретний `sb_secret_...`; підтримується також legacy service_role).
4. Секрети ніколи не мають префікса `PUBLIC_` та не потрапляють у Git або повідомлення.

При поданні анкети одна транзакція створює заявку та запис у черзі сповіщень. Повтор із тим самим ключем або тією ж поштою в межах тієї ж ролі повертає початковий ID, не створюючи дубль. Нова подача не перезаписує попередні відповіді; щодо виправлень заявник звертається до команди. Учасницька й спікерська анкети однієї людини можуть існувати окремо.

## Підключення Telegram

1. Створити бота через офіційний BotFather.
2. Додати його в закриту групу організаторів із правом надсилати повідомлення й файли. Надмірні права адміністратора боту не потрібні.
3. Заповнити `TELEGRAM_BOT_TOKEN`, числовий `TELEGRAM_CHAT_ID` та `TELEGRAM_ADMIN_IDS` (через кому). Кнопки та команди працюють лише для цих людей і лише в цій групі.
4. Згенерувати незалежні `TELEGRAM_WEBHOOK_SECRET`, `RATE_LIMIT_SECRET` і `CRON_SECRET`, кожен щонайменше з 32 випадкових символів; для webhook використати літери, цифри, `_` або `-`.
5. Після розгортання задати HTTPS `SITE_URL` й виконати:

```powershell
npm run telegram:setup
```

Бот надсилає коротку заявку. «Повна анкета» показує всі відповіді в групі. Кнопки змінюють внутрішній статус, фіксують ID організатора та зберігають історію. Помилкове рішення можна змінити, включно з поверненням у «Нові». Автоматичних листів і повідомлень заявникам немає.

Команди для групи:

- `/help` — інструкція;
- `/export_participants` — CSV анкет учасників;
- `/export_speakers` — CSV анкет спікерів;
- `/retry` — опрацювати до п’яти доступних сповіщень із черги.

## Черга й повтори

Надсилання у Telegram виконується після транзакції збереження. Збій не видаляє заявку. Черга обробляється при нових поданнях, командою `/retry` і через захищений cron endpoint. `vercel.json` містить щоденний запуск о 09:00 UTC, сумісний із обмеженням Hobby; він обробляє до п’яти записів за запуск. Для своєчасного відновлення після тривалого збою або великої черги налаштувати частіший зовнішній планувальник чи змінити розклад на тарифі, що його підтримує. Запит має передавати `Authorization: Bearer <CRON_SECRET>`.

Доставка має семантику «щонайменше один раз»: якщо Telegram прийняв повідомлення, але запис підтвердження в базу зірвався, після повтору можливий дубль повідомлення з тим самим ID заявки. Власне заявка не дублюється. Обмеження Telegram зберігають завдання в черзі для повтору. Хеші для обмеження спроб очищуються через добу під час наступних звернень; IP в заявці не зберігається.

## Розгортання на Vercel

1. Імпортувати цей каталог як окремий репозиторій або вказати його як **Root Directory** `forum-national-identity` для окремого Vercel-проєкту.
2. Framework: Astro; install: `npm ci`; build: `npm run build`. Використати Node.js 22 або 24 відповідно до engines залежностей.
3. Додати всі значення з `.env.example` у потрібне середовище Vercel. Для Preview залишити `REGISTRATION_OPEN=false` і використовувати тестові сервіси.
4. Перевірити підключення, реальне тестове подання, статуси, експорт і cron.
5. Організатор має завершити та підтвердити повідомлення `/privacy`: реквізити відповідальної сторони, строк зберігання й організаційний процес врахування рішення щодо зйомки. Вміст сторінки — робоча редакція, що потребує цих фактичних уточнень.
6. Лише після цього встановити `REGISTRATION_OPEN=true` й повторно розгорнути. Код повертає відкритий статус лише коли також налаштовані Supabase, Telegram і секрет обмеження спроб.

Vercel deployment protection не має блокувати робочий Telegram webhook. Перед відкриттям реєстрації перевірити доступ до нього без браузерної авторизації (сам маршрут перевіряє секретний заголовок Telegram). Вартість і придатність тарифів Vercel/Supabase визначає власник акаунтів перед запуском.

## Субдомен

Додати `forum.pmu.org.ua` у Settings → Domains окремого проєкту Vercel. У DNS `pmu.org.ua` додати CNAME `forum` зі значенням, яке покаже Vercel; перевірити домен і HTTPS. Змінити `SITE_URL`, повторити збірку, а потім `npm run telegram:setup`. Canonical та Open Graph URL беруться з `SITE_URL`, внутрішні посилання відносні.

## Що залишається перед реальним запуском

Локація, остаточний розклад, склад спікерів, дедлайн заявок та уточнення повідомлення про персональні дані ще не надані. Ці факти не вигадуються. Налаштування реальних акаунтів і контрольне подання потрібні для підтвердження роботи зовнішніх інтеграцій; локальні тести використовують підміни HTTP і не надсилають персональних даних.
